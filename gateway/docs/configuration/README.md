# Конфигурация Go gateway

Контракт текущей реализации Go gateway. Gateway — самостоятельное Go-приложение с app- и infra-логикой. Session, CSRF, authorization, trusted IP, лимиты, error pages, maintenance и CSP выносятся во внешние интерцепторы. Возможности исходной конфигурации, выполняемые локально, сохраняются в gateway, включая Basic Auth и динамические заголовки. `dynamicTarget` исключён по отдельному решению.

- [Gateway Definition](gatewaydefinition.md) — глобальные настройки.
- [Service Definition](servicedefinition.md) — маршруты и объявления внешних интерцепторов.
- [Secret Definition](secretdefinition.md) — именованные секреты.
- [Примеры YAML](examples/) — согласованный пример gateway, backend и двух интерцепторов.

## Загрузка и merge

Каждый YAML-документ содержит обязательный `kind`. Неизвестные поля, некорректные значения и ссылки на отсутствующие объекты — ошибки конфигурации. Валидация и компиляция всех regexp выполняются до начала обслуживания запросов.

`weight` — целое число, по умолчанию `0`; для Secret Definition также сохранены исходные `min` / `max` как самый низкий / высокий приоритет. Чем больше вес, тем выше приоритет. При одинаковом весе можно сохранить порядок загрузки; контракт не гарантирует порядок между документами одного веса. Если порядок влияет на поведение, следует назначить разные веса или описать маршруты в одном документе.

Глобальные настройки и секреты объединяются от меньшего веса к большему:

- Указанное скалярное значение заменяет предыдущее, включая `false`, `0`, `0s` и пустую строку.
- Отсутствующее поле сохраняет предыдущее значение.
- Объекты и словари объединяются по ключам рекурсивно.
- Обычные списки заменяются целиком, включая явно заданный пустой список.
- Значения по умолчанию применяются после merge. `null` не используется для удаления или сброса полей и считается ошибкой.

**Маршруты имеют отдельное правило:** документы `gateway/service/v1` сортируются от большего веса к меньшему, затем их списки `routes` последовательно конкатенируются. Порядок маршрутов внутри каждого документа сохраняется; `patterns` не меняет позицию маршрута. Первый маршрут, совпавший по пути и `headerMatch`, выбирается для обработки.

Документы с одинаковым `name` разрешены. Их маршруты не заменяют друг друга: каждый блок `routes` занимает позицию, заданную весом исходного документа. Блоки `interceptor` одного имени объединяются по общим правилам merge; итоговое имя используется как `id` внешнего интерцептора.

Например, документ с `weight: 100` содержит специальные маршруты, а документ с `weight: -100` — общий fallback `^/.*$`. Специальные маршруты всегда проверяются раньше fallback, независимо от порядка загрузки файлов.

## Regexp и параметры пути

Преобразование определяется полем конфигурации, а не содержимым строки. В обычных regexp-полях `{name}` не преобразуется в именованную группу: выражение передаётся в Go `regexp` без дополнительной обработки. Специальная обработка применяется к полям `pathParametersPattern` у интерцепторов и динамических заголовков.

Для маршрутизации используются стандартные Go regexp: `pattern`, `patterns`, `headerMatch.valueRegex`, `rewrite.old` и `internalRedirect.old`. В `rewrite.new` и `internalRedirect.new` действуют стандартные replacement-правила Go: `$1`, `$2`, `${name}` и `$$` для literal `$`. Обычные группы не требуют именования:

```yaml
rewrite:
  old: '^/backend/(.*)$'
  new: '/$1'
```

Именованные группы Go `(?P<name>...)` / `(?<name>...)` также допустимы, с подстановкой `${name}`. Формат `{name}` не является подстановкой в rewrite или internal redirect. См. [документацию Go regexp](https://pkg.go.dev/regexp/syntax#hdr-Syntax).

`interceptors[].pathParametersPattern` и `addHeaders.*.pathParametersPattern` — шаблоны извлечения параметров пути. В нём поддерживается удобный формат `{name}`: gateway преобразует его в именованную группу `(?P<name>[^/]+)` перед компиляцией Go regexp. Остальная часть шаблона сохраняет синтаксис Go regexp, включая обычные и явно именованные группы.

Например, `^/api/users/{user_id}$` преобразуется в `^/api/users/(?P<user_id>[^/]+)$`. Для пути `/api/users/42` в запросе Intercept передаётся `pathParameters: {user_id: "42"}`. Параметры извлекаются из пути после rewrite и internal redirect. Сам URL при извлечении не меняется; словарь передаётся внешнему интерцептору, а не добавляется в ответ конечному HTTP-клиенту.

Placeholder захватывает один непустой сегмент пути. Для другого ограничения можно явно записать Go-группу, например `(?P<user_id>[0-9]+)`. Имя placeholder начинается с ASCII-буквы или `_`, далее допускаются буквы, цифры и `_`; имена групп должны быть уникальны. Числовые квантификаторы `{2}` и `{1,3}` сохраняются. Экранированные `\{` и `\}` обозначают literal скобки и не преобразуются в группы.

`pathParametersPattern` — поле конфигурации, задающее специальный шаблон. У интерцептора извлечённые значения передаются в API-словаре `pathParameters`; у `addHeaders` они локально подставляются в `value` через `{name}`. Вызов внешнего сервиса для динамических заголовков не требуется. Неизвестное имя в `value` — ошибка конфигурации; `{{` и `}}` позволяют задать literal скобки в динамическом шаблоне. Без `pathParametersPattern` значение заголовка статическое.

Env-подстановки `$(VAR)` / `$(VAR:-default)` выполняются при загрузке конфигурации и не меняют правила regexp. Для regexp и replacement рекомендуются одинарные кавычки YAML.

## Порядок обработки запроса

1. Выбрать первый маршрут по текущему пути и `headerMatch`. Если такого нет — `404`.
2. Проверить `allowedMethods` выбранного маршрута. При запрете завершить запрос; следующие маршруты не рассматриваются.
3. Выполнить `rewrite`, затем `internalRedirect` над получившимся путём. При внутреннем переходе повторить выбор маршрута и его встроенные операции. Интерцепторы промежуточных маршрутов не вызываются.
4. Удалить входные заголовки из `internalHeaders` перед внешними интерцепторами.
5. Выполнить локальный Basic Auth конечного маршрута.
6. Выполнить включённые request-фазы интерцепторов конечного маршрута в порядке объявления внутри каждой фазы. Каждый следующий интерцептор получает состояние с уже применёнными изменениями предыдущего, включая сессионные заголовки. Они получают уже преобразованный путь.
7. Вернуть `directResponse` или проксировать запрос в `target`.
8. Применить отложенные изменения заголовков ответа из request-фаз, затем включённые response-фазы интерцепторов, затем локальные статические/динамические `addHeaders`. Правила приоритета заголовков описаны в Service Definition.

Query, метод и тело запроса сохраняются при rewrite и internal redirect. Внешние интерцепторы получают заголовки, тело и trailers только в фазах, включённых в `processingMode`. Без body processing тела передаются потоком; при включённом buffered body действуют явные лимиты. Контракт позволяет авторизацию и изменение запроса/ответа, см. [API интерцепторов](../api/README.md).

## Границы и предложения для review

Встроенные типы интерцепторов и их конфигурации (session, CSRF, trusted IP, overdraft, securityAccess) отсутствуют. Error pages, maintenance и CSP также выносятся во внешние интерцепторы; gateway не обращается к сервису страниц ошибок напрямую. `accountAddress` и Redis-настройки встроенных интерцепторов исключены как зависимости от внешних сервисов. `dynamicTarget` не реализуется по ранее принятому решению.

Локальные возможности исходной конфигурации сохраняются: routing, rewrite, internal redirect, ограничения методов, Basic Auth, заголовки, секреты, таймауты, HTTP/2 и порты. Отдельный `interceptorServer` для исполнения встроенных интерцепторов не нужен: gateway вызывает внешние интерцепторы как клиент.

Направление сортировки веса, правила merge списков, лимит внутренних переходов, точная семантика idle timeout, HTTP-статусы ошибок и правила наложения заголовков закреплены в этом контракте и реализованы.

Basic Auth проверяется до внешних интерцепторов. Rewrite и internal redirect всегда предшествуют интерцепторам. Maintenance можно поставить после session в request-цепочке, чтобы он получил сессионные данные предыдущего интерцептора.

## API интерцепторов и error pages

Go реализует HTTP proxy и control plane загрузки/подготовки конфигурации. Envoy, xDS и Lua в текущей реализации не используются: они не требуются для ожидаемой нагрузки.

[API интерцепторов](../api/README.md) расширен по фазовой модели ext_proc: request/response headers, buffered body и trailers. Решение — продолжить обработку с mutations или вернуть немедленный ответ. Исходный draft API заменён; фазы выбираются в `processingMode` каждой записи `route.interceptors`.

Error pages — внешний response-интерцептор. Он получает HTTP status на `responseHeaders` и может заменить тело страницы без чтения исходного ответа. Gateway не обращается к отдельному сервису страниц ошибок через встроенную функцию. Отказ авторизации также оформляется готовым ответом интерцептора.

CSP, включая генерацию nonce и согласование с backend, реализует внешний интерцептор через request/response mutations. Встроенных `maintenance`, `disableMaintenance`, `headerOnlyMaintenance` и `cspHeaders` нет. `gatewayHealthHost` реализован как дополнительный health listener (default 8082, `0` выключает). Ненулевой `gatewayPort` отклоняется: управляющий API пока не определён. Hot reload в этом контракте не описывается.
