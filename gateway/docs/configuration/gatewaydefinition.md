# Gateway Definition

Конфигурация самого gateway — порты, таймауты и глобальные инфраструктурные настройки

---

## Краткое введение

Файл описывает глобальные параметры gateway: порты, таймауты проксирования и очистку внутренних заголовков. Поле `kind` должно быть равно `gateway/v1`. Допускается несколько файлов — они объединяются (merge) в одну конфигурацию; файл с более высоким `weight` имеет приоритет. При равных весах порядок не гарантируется. Правила merge описаны в [общем контракте](README.md#загрузка-и-merge).

---

## Шпаргалка

| Поле                | Тип    | Обязательное | Описание                                           | Значение по умолчанию |
|---------------------|-------:|:------------:|----------------------------------------------------|----------------------|
| `kind`              | string |      да      | тип/версия конфига                                 | `gateway/v1`         |
| `weight`            |    int |     нет      | приоритет конфигурации при merge                   | `0`                  |
| `port`              |   uint |     нет      | порт основного HTTP-прокси                         | `8000`               |
| `healthzPort`       |   uint |     нет      | порт liveness/readiness пробы                      | `15000`              |
| `gatewayPort` | uint | нет | зарезервирован; допустимо только `0` | `0` |
| `gatewayHealthHost` | uint | нет | дополнительный health listener; `0` выключает | `8082` |
| `proxyTimeouts`     | object |     нет      | глобальные таймауты проксирования                  | —                    |
| `internalHeaders`   | object |     нет      | список внутренних заголовков, удаляемых из запроса  | —                    |

## Краткий пример конфигурации

```yaml
kind: gateway/v1
weight: 100

port: 8000
healthzPort: 15000
proxyTimeouts:
  timeout: 60s
  idleTimeout: 600s
```

---

## Подробное описание полей

### port

Порт основного HTTP-прокси, на который поступают пользовательские запросы.

- Тип: `uint`
- По умолчанию: `8000`

### healthzPort

Порт для liveness/readiness проб. Endpoint: `/healthz`, `/readyz`. Readiness успешна после загрузки конфигурации и запуска proxy listener; при завершении приложения readiness отключается.

- Тип: `uint`
- По умолчанию: `15000`

### gatewayPort / gatewayHealthHost

`gatewayHealthHost` — дополнительный listener тех же health endpoint, default `8082`. Явное `0` выключает его; если порт совпадает с `healthzPort`, отдельный listener не создаётся. Ненулевой `gatewayPort` отклоняется при валидации: управляющий API не определён. Эти поля не задают адрес внешнего сервиса.

### proxyTimeouts

Глобальные таймауты проксирования запросов. Применяются к маршрутам, у которых не указаны собственные таймауты.

```yaml
proxyTimeouts:
  timeout: 60s
  idleTimeout: 600s
```

| Поле | Тип | Описание | По умолчанию |
|------|-----|----------|--------------|
| `timeout` | duration | общий срок проксирования: от начала отправки запроса upstream до завершения передачи ответа клиенту | `1m` |
| `idleTimeout` | duration | допустимое отсутствие данных от upstream после отправки запроса | `10m` |

Отсутствующее поле наследует глобальное значение, а глобальное отсутствующее поле получает default после merge. Явное `0s` отключает соответствующий таймаут; отрицательные значения запрещены.

`idleTimeout` действует, когда запрос уже отправлен, а upstream ещё его обрабатывает: до первых данных ответа, затем между поступлениями данных ответа. После получения данных отсчёт начинается заново. Это таймаут активности конкретного запроса, а не срок хранения свободного keep-alive соединения в пуле. Пока тело запроса ещё отправляется, этот таймер не действует.

`timeout` продолжает действовать независимо от активности upstream. Оба таймера завершают проксирование при срабатывании; отключение одного не отключает другой. Таймаут внешнего интерцептора задаётся отдельно в Service Definition.

---

### internalHeaders

Список заголовков, удаляемых из входного запроса перед первым внешним интерцептором (или перед обработкой конечного маршрута, если интерцепторов нет). Интерцепторы могут заново установить эти заголовки; их значения передаются следующим интерцепторам и upstream. Имена заголовков сравниваются без учёта регистра. Для сопоставления маршрута `headerMatch` используется исходный запрос.

```yaml
internalHeaders:
  headers:
    - X-Auth-Account
    - X-Auth-User
```

| Поле      |      Тип | Описание                     |
|-----------|--------:|-------------------------------|
| `headers` | []string | имена внутренних заголовков  |
